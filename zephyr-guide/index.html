先搞懂：RTOS 是什麼？跟 Linux 差在哪？

RTOS（Real-Time Operating System，即時作業系統）的重點不是「快」，而是可預測：一件事情必須在規定的時間內完成，晚一點就算失敗。例如馬達控制要在 1 ms 內更新、心律裝置必須準時取樣。

微控制器（MCU）通常只有幾十 KB 的 RAM、沒有 MMU、沒有硬碟。Linux 跑不起來，而直接寫裸機（bare-metal）程式又很難管理多工、通訊協定與驅動。Zephyr 就落在這兩者之間。

裸機 Bare-metal

while(1) 超級迴圈
  • 最省資源
  • 沒有執行緒、沒有排程
  • 換一顆晶片，驅動幾乎全部重寫
  • 藍牙、網路堆疊要自己整合

Zephyr RTOS

實測最小 2.3 KB Flash（無執行緒）
  • 搶佔式多執行緒、確定性排程（實測含多執行緒 5.9 KB）
  • 統一的驅動 API + Devicetree，換板子只改設定
  • 內建 BLE、TCP/IP、USB、檔案系統、Shell
  • 用 Kconfig 精準裁掉不需要的功能

嵌入式 Linux

通常需數十 MB RAM
  • 功能完整、生態系龐大
  • 需要 MMU 與外部記憶體
  • 開機數秒
  • 即時性需額外修補（PREEMPT_RT）

版本節奏：每半年一版，LTS 支援約五年

Zephyr 以原始碼形式發佈，沒有二進位映像。依 doc/releases/index.rst，主版本每六個月一版（目標 4 月與 10 月），一般版本支援約兩個週期（約一年）；每 2.5 到 3 年選一個版本當 LTS（長期支援），從主線分支出來獨立維護約五年。

入門 02 · Codebase 全貌

打開 repo，先看哪裡？

核心（kernel/）只有 92 個檔案、24,400 行。整個 repo 的大部分是「讓同一個核心能跑在上千種硬體上」的板子定義、驅動、Devicetree 和測試。點選左側長條看每個目錄的角色，也可以切換成「程式碼行數」看重量分佈。

每個頂層目錄的檔案數（所有類型）。銅色＝核心。
閱讀心法：Zephyr 的程式碼很多，但大多是「平行的同類物」：一千多塊板子、上百種驅動類別。只要讀懂一塊板子、一種驅動、一個 sample，其餘都是同一個模式的重複。

不只是 C：三分之一是「描述語言」

C 程式碼約 458 萬行，佔 66%。剩下的三分之一裡，Devicetree（91 萬行）、YAML（27 萬行）、Kconfig（24 萬行）、CMake（12 萬行）與 .conf（7 萬行）加起來約 161 萬行，佔 23%。

這些都是描述語言：描述板子上有什麼硬體、每種裝置有哪些屬性、哪些功能可以開關、測試要在哪些平台跑。Zephyr 的設計重心是把「硬體差異」從 C 程式碼搬到資料檔裡，讓 C 程式碼保持通用。

另外還有 46 萬行 reStructuredText 文件，以及約 20 萬行 Python（大多在 scripts/：west 擴充指令、Devicetree 與 Kconfig 工具、Twister 測試框架）。

洞察：核心 24,400 行只佔全部 C 程式碼的 0.53%。drivers/ 有 168 萬行（37%）、subsys/ 96 萬行、tests/ 73 萬行。Zephyr 真正的工程量在「可攜性」與「協定堆疊」，排程器本身反而是最小的一塊。
進階 03 · 硬體覆蓋版圖

1,703 個建置目標，ARM 佔三分之二

板子的 Twister 描述檔（boards/**/<target>.yaml）裡有 arch: 欄位。數一數就知道 Zephyr 實際支援的硬體分佈：一塊板子可能有多個目標，例如 nRF5340 DK 的應用核心、網路核心、TrustZone 非安全區各算一個。

板子的名字怎麼讀：Hardware Model v2

4.x 的板子用 board.yml 描述，建置目標的完整寫法是 板子[@版本]/SoC/CPU 叢集/變體。例如 Nordic nRF5340 DK 是雙核心晶片，就有三個目標：

boards/nordic/nrf5340dk/board.yml
board:
  name: nrf5340dk
  full_name: nRF5340 DK
  vendor: nordic
  socs:
  - name: 'nrf5340'
    variants:
    - name: 'ns'
      cpucluster: 'cpuapp'
建置目標意義
nrf5340dk/nrf5340/cpuapp應用核心（Cortex-M33）
nrf5340dk/nrf5340/cpuapp/ns應用核心的 TrustZone 非安全區（搭配 TF-M）
nrf5340dk/nrf5340/cpunet網路核心（跑藍牙控制器）
qemu_cortex_m3只有一個 SoC 時可省略，建置時會顯示 qualifiers: ti_lm3s6965

每個目標在板子目錄下都有一組同名檔案：<board>_<qualifiers>.dts（硬體描述）、_defconfig（預設 Kconfig）、.yaml（給 Twister 的測試中繼資料，arch、RAM、支援的功能）。

進階 04 · 架構分層

從硬體到 main()，一層一層往上疊

Zephyr 是一個「單一映像檔」系統：應用程式、核心、驅動在編譯時被靜態連結成一個 zephyr.elf。右側的 Kconfig 與 Devicetree 不是執行期的層，而是在編譯期決定每一層長什麼樣子。點選任一層看說明。

洞察：因為所有東西都在同一個位址空間、同一次連結中產生，Zephyr 不需要動態載入器，也不需要執行期的裝置探測。代價是「改設定就要重新編譯」，換來的是更小的體積與在編譯期就能抓到的錯誤。需要動態載入時，可以用 LLEXT 子系統（第 15 章）。

每開一個功能，要付多少 Flash 與 RAM？

以下數字全部是本頁製作時實際編譯得到的連結器報告（Memory region … Used Size），工具鏈為 arm-none-eabi-gcc 13.2，C 函式庫為 picolibc，最佳化選項為 Zephyr 預設的 -Os。換工具鏈或版本，數字會有小幅差異。

記憶體地圖：連結器把東西放在哪

RAM 的大頭是堆疊

hello_world 用了 4,184 B RAM，其中 3,328 B（80%）是三個堆疊：中斷堆疊 2,048 B（CONFIG_ISR_STACK_SIZE）、main 執行緒 1,024 B（CONFIG_MAIN_STACK_SIZE）、idle 執行緒 256 B。

右邊是在開了 Shell 的版本上，實際輸入 kernel thread stacks 的結果：中斷堆疊配了 2,048 B，開機到現在只用過 216 B。調整堆疊大小，是縮減 RAM 最直接的手段。

另一個觀察：同一個 hello_world，在 nRF52840 上是 21,060 B，幾乎是 QEMU 的兩倍。多出來的是真實硬體需要的支援：時脈控制 1,160 B、GPIO 1,110 B、RTC 計時器 1,220 B、pinctrl 474 B，以及 Nordic 的 nrfx HAL 3,480 B。GPIO 驅動會被編進來，是因為板子的 defconfig 開了 CONFIG_GPIO=y，而 Devicetree 裡啟用的 GPIO 節點讓 CONFIG_GPIO_NRFX 自動預設為 y。

    深入 08 · 執行緒與排程 · kernel/sched.c
    
      
    執行緒、優先權與搶佔
    
      
    Zephyr 的排程器永遠讓「已就緒、優先權最高」的執行緒執行。數字越小，優先權越高。預設設定下共有 32 個等級：-16 到 15。
    
      
    
        
    負數：協作式 cooperative一旦開始執行，不會被其他執行緒搶走 CPU，直到它自己 sleep、等待或 k_yield()。適合不可被打斷的協定處理。系統工作佇列預設在 -1。
    
        
    0 以上：搶佔式 preemptible更高優先權的執行緒一就緒，就立刻搶走 CPU。main() 預設在優先權 0 執行，應用程式可用到 14。
    
        
    ISR：中斷服務程序不屬於執行緒，硬體中斷會打斷任何執行緒。ISR 要短，通常只是 k_sem_give() 喚醒工作執行緒。
    
      
    

      

      

      
    執行緒的一生：狀態位元
    
      

      
    就緒佇列有三種實作，可以用 Kconfig 換
    
      
    
        
    
          
    Kconfig資料結構插入成本適合
    
          
            
    SCHED_SIMPLE（預設）依優先權排序的雙向鏈結串列O(n)執行緒少的系統，程式碼最小
    
            
    SCHED_SCALABLE紅黑樹O(log n)執行緒很多（數十個以上）
    
            
    SCHED_MULTIQ每個優先權一條串列 + 點陣圖O(1)要求固定時間；不能和 EDF（SCHED_DEADLINE）並用
    
              
        
    
      
    
      
    實作都在 header-only 的 kernel/include/priority_q.h。等待佇列另有 WAITQ_SIMPLE（預設）與 WAITQ_SCALABLE 兩種。有趣的是，本頁實測的 qemu_cortex_m3 板子在自己的 defconfig 裡選了 CONFIG_SCHED_MULTIQ=y，覆蓋了核心預設值。
    

      
    
        
    
          
    同優先權怎麼分：time slicing 與 EDF
    
          
    Time slicing（CONFIG_TIMESLICING，預設開）：同優先權的搶佔式執行緒，每跑滿 CONFIG_TIMESLICE_SIZE（預設 20 ms）就輪到下一個。實作在 kernel/timeslicing.c，由系統時鐘中斷尾端的 z_time_slice() 檢查。
    
          
    EDF（CONFIG_SCHED_DEADLINE）：用 k_thread_deadline_set() 設截止時間。注意它只在相同靜態優先權的執行緒之間決定先後，不會讓低優先權的執行緒越過高優先權的。
    
          
    SMP：多核心需要 CONFIG_USE_SWITCH（以 arch_switch 取代 arch_swap），核心之間用 IPI 通知重新排程，k_thread_cpu_pin() 可以把執行緒綁在特定 CPU。
    
        
    
        
    容易誤會的一點：協作式執行緒呼叫 k_sem_give() 喚醒一個更高優先權的執行緒時，不會立刻被搶佔。update_cache()（kernel/sched.c:167）只在目前執行緒可被搶佔時才更新「下一個要跑誰」；協作式執行緒要等到自己睡眠、等待或 yield，被喚醒的執行緒才會上場。

    深入 10 · 時間與計時器 · kernel/timeout.c
    
      
    Tick、tickless 與逾時佇列
    
      
    核心所有和時間有關的功能（k_sleep、等待逾時、k_timer、延遲工作、time slicing）共用同一個逾時佇列。系統計時器驅動只負責兩件事：在下一個逾時到期時產生中斷，以及回報「過了幾個 tick」。
    
      

      
    
        
    
          
    
            
    情況Tick 頻率1 tick
    
            
              
    QEMU 目標（本頁實測 qemu_cortex_m3）100 Hz10 ms
    
              
    tickless 核心的一般預設10,000 Hz0.1 ms
    
              
    Nordic nRF（本頁實測 nRF52840）32,768 Hz≈ 30.5 µs
    
                
          
    
        
    
        
    
          
    k_timeout_t 其實只是包了一個 tick 數的結構（sys/clock.h:65）。K_MSEC(ms) 會無條件進位成 tick；相對逾時在加入佇列時還會再加 1 tick，確保至少等滿指定時間（timeout.c:216）。
    
          
    所以在 100 Hz 的板子上，k_msleep(1) 實際會睡 10 到 20 ms。需要毫秒以下的精準延遲，要用 k_busy_wait() 或硬體計時器，而不是 sleep。
    
          
    Tick 頻率由 SoC 或板子決定：全 tree 有 82 個 Kconfig 檔改寫了 SYS_CLOCK_TICKS_PER_SEC。
    
        
    
      
    

      
    逾時佇列也可以換資料結構（實驗中）
    
      
    
        
    
          
    CONFIG_TIMEOUT_BACKEND_…結構狀態
    
          
            
    DLIST（預設）依到期時間排序的差值串列：插入 O(n)，取出最早的 O(1)穩定

    WHEEL計時輪：32 個「近期」與 32 個「稍後」串列，加上一條遠期排序串列EXPERIMENTAL
    
            
    BUCKET每個 tick 一個桶，加上溢出串列EXPERIMENTAL
    
            
    SKIPLIST跳躍串列（Pugh skip list）EXPERIMENTAL

    附錄 22 · 名詞速查
    
      
    看到這些詞時
    
      
    
        
    west
    Zephyr 的命令列工具：管理多 repo 工作區（west.yml）、編譯、燒錄、除錯、跑測試。
    
        
    Board / SoC
    板子（boards/）描述一塊實體電路板；SoC（soc/）描述上面的晶片。板子名稱格式如 nrf52840dk/nrf52840。
    
        
    HWMv2 qualifiers
    建置目標中板子名稱之後的部分：/SoC/CPU 叢集/變體，例如 nrf5340dk/nrf5340/cpuapp/ns。
    
        
    Devicetree
    描述硬體的資料格式。.dts 描述板子，.overlay 讓應用程式覆寫設定，bindings 定義每種裝置可用的屬性。
    
        
    compatible / binding
    compatible = "bosch,bme280" 指出節點是哪種裝置；dts/bindings/ 下同名的 YAML 規定它有哪些屬性。
    
        
    DT ordinal
    建置時依相依關係排序後給每個 Devicetree 節點的序號，裝置物件命名為 __device_dts_ord_N。
    
        
    Kconfig
    來自 Linux 的功能設定系統。prj.conf 開關功能，產生 .config 與 autoconf.h。
    
        
    Init level
    開機初始化的階段：EARLY、PRE_KERNEL_1、PRE_KERNEL_2、POST_KERNEL、APPLICATION、SMP。
    
        
    Iterable section
    用連結器區段收集同類物件（裝置、shell 指令、log 模組…），執行期用 STRUCT_SECTION_FOREACH 走訪。
    
        
    z_impl / z_vrfy / z_mrsh
    系統呼叫的三個部分：實作、權限驗證、參數拆解。後者由 gen_syscalls.py 產生。
    
        
    PendSV
    Cortex-M 上優先權最低的例外，Zephyr 用它執行 context switch。
    
        
    Tickless
    沒有到期的逾時就不產生週期中斷，讓 CPU 睡更久。
    
        
    Work queue
    專門執行「工作項目」的執行緒。ISR 把需要較長處理的事情丟給它，系統工作佇列預設在優先權 -1。
    
        
    MetaIRQ
    一種特殊的最高優先權協作式執行緒，可以搶佔其他協作式執行緒，用來把中斷的後半段處理搬到執行緒中。
    
        
    Module
    不在主 repo 的外部程式庫（HAL、mbedTLS、LVGL…），透過 west.yml 引入，目前列出 80 個專案，其中 29 個是廠商 HAL。
    
        
    HAL
    晶片廠商提供的硬體抽象層（例如 Nordic 的 nrfx），Zephyr 驅動常建立在它之上。
    
        
    picolibc
    Zephyr 預設的 C 函式庫，針對小型嵌入式系統設計。另有 minimal libc 可選。
    
        
    Sysbuild
    一次建置多個映像，例如 MCUboot bootloader + 應用程式，或多核心晶片的每個核心。
    
        
    MCUboot / mcumgr / SMP
    MCUboot 是安全開機與韌體更新的 bootloader；mcumgr 是裝置管理框架，透過 SMP 協定在 BLE、UART、UDP 上傳輸新映像。
    
        
    RTIO
    Real-Time I/O：以提交佇列與完成佇列做非同步 I/O，新版感測器 API 建立在它之上。
    
        
    zbus
    執行緒之間的發布／訂閱訊息匯流排，用編譯期定義的通道與觀察者解耦模組。
    
        
    SMF
    State Machine Framework：支援階層式狀態的狀態機框架（lib/smf）。
    
        
    LLEXT
    Linkable Loadable Extensions：在執行期載入、連結並執行 ELF 擴充模組。
    
        
    Twister
    測試執行器，自動在多個平台上編譯並執行 tests/ 與 samples/。
    
        
    ztest
    Zephyr 的單元測試框架：ZTEST_SUITE、ZTEST、zassert_*。
    
        
    native_sim
    把 Zephyr 編譯成 Linux 執行檔的「板子」，不需要硬體就能開發與測試。
    
        
    BabbleSim
    模擬 2.4 GHz 無線環境的模擬器，讓多台虛擬藍牙裝置在 CI 中互相通訊。
    
        
    Snippet / Shield
    Snippet 是可重複使用的設定片段（如切換 console）；Shield 是外接擴充板的 Devicetree 描述。
    
        
    LTS
    長期支援版本，產品開發通常選 LTS 以獲得長時間的安全修補。目前是 3.7（支援到 2029-07-27）。
